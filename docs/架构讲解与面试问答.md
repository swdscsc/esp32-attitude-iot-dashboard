## 一、这个项目解决什么问题

原项目（esp32-qmi8658-attitude-monitor）的输出终点是"本地屏幕"：数据在哪采集就只能在哪看。
真实物联网系统需要的是**数据脱离设备本体**：远程可看、可存、可分析、可反控。

本项目把终点延伸到云端，形成闭环：
**传感 → 上云 → 存储 → 分析 → 反向控制**。麻雀虽小，五脏俱全。

## 二、数据流与关键技术点

### 1. 设备端（ESP32-S3）

```
Qmi8658_Read_Acc()          拿原始加速度（int16，寄存器值）
   ↓
qmi8658_fetch_angleFromAcc()  atan 换算成三轴倾角（float，度）
   ↓
snprintf 拼 JSON             {"ax":12.30,"ay":-3.10,"az":88.50}
   ↓
esp_mqtt_client_publish()    QoS=1 发布到 .../data，500ms 一帧
```

**为什么用 MQTT 而不是 HTTP？**
- HTTP 是"请求-响应"，设备要主动轮询，开销大；MQTT 是发布/订阅，长连接，一有数据就推
- 报文头最小 2 字节（HTTP 头几百字节起），对嵌入式设备的带宽和功耗友好
- 天然支持一对多：设备发一条，订阅的采集器、监控面板、手机同时收到
- 内置 QoS 和遗嘱消息（LWT），弱网环境可靠

**为什么 QoS 用 1 不用 0 / 2？**
- QoS 0 最多一次：丢帧无感知，姿态监控漏几帧可接受但对"断链检测"不利
- QoS 1 至少一次：PUBACK 确认，可能重复但不丢——监控场景重复帧无害（分析端可去重）
- QoS 2 恰好一次：四次握手，延迟和实现复杂度最高，这个场景不值得

**未连接时发的数据去哪了？（诚实回答：丢了）**
当前版本 `mqtt_app_is_connected()` 为假时直接 return 丢帧。
改进方案是加环形缓冲区，重连后带时间戳补传——这也是 README 里的后续计划之一。
（面试官问局限性能答出这一条，比背十条优点加分）

### 2. 数据端（Python）

- **为什么用 SQLite 不用 CSV/MySQL？**
  CSV 无索引、并发写会坏文件；MySQL 对单机实验是杀鸡用牛刀。
  SQLite 单文件、零配置、带索引（按 ts 建了索引），后续按时间段查询是 O(log n)。
- **collector 每 10 条 commit 一次**：SQLite 每条 commit 都是一次 fsync，500ms 一帧逐条提交没有意义，批量落库是常规工程习惯。
- **异常报文处理**：JSON 解析失败就丢弃并打印原始 payload——公共 Broker 上什么报文都有，解析端必须防御性编程。

## 三、面试 Q&A 实录预演

**Q: 数据量大了怎么办？**
SQLite 单机写并发有限。升级路径：SQLite → InfluxDB/TDengine（时序数据库，自带降采样）→ 数据量大后 Kafka 削峰。关键是能说清"什么时候该换"：写入速率超过单盘 fsync 能力或需要多客户端并发写时。

**Q: 怎么保证设备在线状态？**
MQTT 遗嘱消息（LWT）：连接时设置 will topic 为 `.../status`、payload `offline`，设备异常掉线时 Broker 代发。当前代码在 CONNECTED 时主动发 `online`（retained），配合 LWT 形成"上线/掉线"状态机。

**Q: 安全性怎么考虑？当前缺什么？**
当前是公共 Broker 裸奔，仅适合测试。生产方案三层：
1. 传输层：TLS（8883 端口）防窃听
2. 认证层：用户名密码 / 客户端证书
3. 授权层：每设备只能发布自己的主题前缀（ACL）
能主动说出"当前缺什么"比假装安全更加分。

**Q: 姿态解算为什么只用加速度计？不是有六轴吗？**
用 `atan2(ax, sqrt(ay²+az²))` 这类公式从重力向量反推倾角——静止时准，但运动加速度会污染结果。
完整方案要陀螺仪积分（短时准、长时漂移）做互补滤波或卡尔曼融合。这是原项目和本项目的共同局限，也是可以继续做的方向。

**Q: 如果让你扩展，做什么？**
1. 断线缓存补传（环形缓冲）
2. 接入时序数据库 + Grafana 面板
3. 异常检测：倾角超阈值推送到手机（mqtt → server酱/企业微信机器人）
4. OTA：云端下发固件升级
